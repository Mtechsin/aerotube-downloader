# Plan: Fix Android Limited Resolution Issue (338p)

## Problem Summary

**Windows**: Works perfectly - fetches all resolutions (144p to 4K) with separate video/audio streams, merges with FFmpeg.

**Android**: Only gets combined video with max ~338p resolution.

## Root Cause Analysis

1. **Missing `--extractor-args` in download**: The `downloadVideo()` method in `MainActivity.kt` (lines 293-354) does NOT pass the `--extractor-args` option that tells yt-dlp to fetch all format streams. Without this, the youtubedl-android library defaults to its internal `android_sdkless` player client which YouTube limits to ~338p maximum.

2. **Inconsistent configuration**: Windows uses comprehensive extractor args:
   ```
   youtube:player_client=web,android,mweb,ios;formats=all
   ```
   Android's `getVideoInfo()` uses `player_client=media` (duplicated on lines 190/196), but `downloadVideo()` has NO extractor args at all.

3. **Secondary issue**: The default format strings differ between platforms. Windows uses a robust fallback chain; Android uses simple "best" fallback.

## Evidence from yt-dlp Issues

- GitHub Issue #15737: "Can only download YT videos in 320p when using the -android_sdkless ffmpeg workaround"
- GitHub Issue #16150: "The `android_vr` player_client has become erratic, often returning ONLY `-f=18`"
- These confirm YouTube limits the `android_sdkless` client to low-bitrate streams

## Solution

### 1. Fix `MainActivity.kt downloadVideo()` - CRITICAL

Add `--extractor-args` EXACTLY as Windows does, BEFORE the format selection.

**Location**: `MainActivity.kt` lines 293-354 (downloadVideo method)

**Change**: After line 322 (after `request.addOption("--user-agent", userAgent)`), add:

```kotlin
// CRITICAL: Request ALL formats including separate video/audio streams
// Without this, the android_sdkless client only provides low-resolution streams (~338p max)
request.addOption("--extractor-args", "youtube:player_client=web,android,mweb,ios;formats=all")
```

This explicitly tells yt-dlp to use web/mobile clients instead of the limited android_sdkless client, and to fetch ALL format streams.

### 2. Update `MainActivity.kt` default format string

Currently (lines 308-312):
```kotlin
if (format != null && format.isNotEmpty()) {
    request.addOption("-f", format)
} else {
    request.addOption("-f", "best")
}
```

Replace with Windows' comprehensive fallback chain (from `ytdlp_service.dart` lines 609-612):
```kotlin
if (format != null && format.isNotEmpty()) {
    request.addOption("-f", format)
} else {
    // Best quality with robust fallback chain (matches Windows implementation)
    request.addOption("-f", "bestvideo[ext=mp4]+bestaudio[ext=m4a]/bestvideo+bestaudio/best[ext=mp4]/best")
}
```

This ensures that when no specific format is requested (like in the UI's "Best Quality" option), yt-dlp tries multiple strategies to get separate streams first.

### 3. Clean up `getVideoInfo()` duplicate extractor args

While not causing the bug, `getVideoInfo()` (lines 163-248) has duplicate `--extractor-args` on lines 190 and 196. Remove the duplicate (keep only one). However, this is low priority as it doesn't break functionality.

### 4. Update `config.txt` (assets)

Current content:
```
--no-mtime
-o /sdcard/Download/youtubedl-android/%(title)s.%(ext)s
-f "bestvideo[ext=mp4]+bestaudio[ext=m4a]/best[ext=mp4]/best"
```

Update to match Windows' approach more closely:
```
--no-mtime
-o /sdcard/Download/youtubedl-android/%(title)s.%(ext)s
-f "bestvideo[ext=mp4]+bestaudio[ext=m4a]/bestvideo+bestaudio/best[ext=mp4]/best"
--extractor-args "youtube:player_client=web,android,mweb,ios;formats=all"
```

**Note**: The config.txt is used as default options by youtubedl-android. Adding extractor args here provides a fallback if individual requests don't specify them.

## Why This Works

- `player_client=web,android,mweb,ios` tells yt-dlp to simulate web/mobile browsers instead of the `android_sdkless` client
- YouTube's servers return different (higher quality) streams for these clients
- `formats=all` ensures yt-dlp fetches every available stream, including separate video-only and audio-only DASH streams
- The format selection string prioritizes separate streams (bestvideo + bestaudio) and falls back gracefully

## Risks & Mitigations

- **Risk**: Some older devices may not support certain codecs. The fallback chain handles this.
- **Risk**: Using `web,android,mweb,ios` might trigger bot detection. The existing retry logic in `getVideoInfo()` can be extended to `downloadVideo()` if needed (but not included in initial fix to keep it simple).
- **Risk**: Larger file sizes. This is expected for high quality - user should have storage awareness.
